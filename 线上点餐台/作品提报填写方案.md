# 作品提报 · 三部分填写方案

> 对应表单：第 1 步 / 共 5 步 · 基本信息（作品名称、一句话介绍、作品说明）
> 所有方案均基于 `线上点餐台` 实际实现，数字可直接核对：5 家 3D 门店 / 13 家 MCP 门店 / 13 分类 100+ 商品 / 158 项营养 / 15 场活动 / 3 张券 / 73 项自测。

## 一、作品名称（建议 ≤ 14 字）

| 方案 | 名称 | 适用场景 | 关键要素 |
| --- | --- | --- | --- |
| A（推荐） | 一个看得见的麦当劳点餐台 | 通用提报、大众投票、展板标题 | 口语化 + 动词「看得见」点出可视化差异 + 品类词「点餐台」交代形态；与原填写一脉相承，只做加固 |
| B | 麦当劳像素 3D 点餐台 | 技术评审、项目文档、GitHub 仓库名 | 品牌 + 风格（像素）+ 技术形态（3D）三要素齐全，最不容易被误解，但记忆点弱 |
| C | 麦门环游记：五家门店的点餐台 | 路演开场、需要故事的场合 | 借「麦门」社区梗拉近距离，「五家门店」把工程量前置，副标题补充形态 |
| D | 看得见的门店，点得到的套餐 | 偏营销 / 传播物料 | 对偶句式，两组「看得见—点得到」形成节奏，适合海报与短视频封面 |

## 三、作品说明

### 可套用的五段骨架

1. **定位**：一句话说清是什么、给谁。
2. **使用方式**：跟着用户走一遍（进入页 → 堂食 / 外卖 → 选餐 → 结算），2–3 个动作即可，不要写成功能目录。
3. **亮点**：3 条，每条都必须挂一个可验证的证据（数字、机制、细节）。
4. **实现思路**：数据层 → 表现层 → 交互层 → 工程校验，讲清「为什么这样做」而不只是「用了什么」。
5. **边界与下一步**：主动交代 demo 的局限，评委最认这一段的诚实度。

---

### 方案 A · 完整叙事版（约 800 字，推荐用于表单正文）

**适用场景**：提报表单的正式填写位、作品详情页、展板正文。
**关键要素**：以「走进去」为主线，把功能写成路径；所有亮点都带数字；结尾主动交代边界。

「一个看得见的麦当劳点餐台」把点餐从一张菜单页，搬进了一间可以走进去的 3D 门店。

打开进入页，先选堂食还是外卖。选堂食，进入 3D 点餐台：左侧是像素风大字标题与门店档案，右上角是这家店的三维模型——富士山下店、广州沙面店、丽都大酒店店、圣托利温泉庄园店、墨尔本 Kew 店，共 5 家真实门店按实景建模，可用鼠标环绕观察但不可缩放，保证每一家都停在最好看的机位。换一家店，模型、店名与欢迎弹窗同步切换；没有模型的 8 家门店自动轮播实景照片，不留空位。页面没有昼夜开关：18:00 之后打开，灯光与整体色调会自行沉入夜晚，富士山店甚至备了日、夜两套模型，切换时用 1.4 秒交叉淡化，不闪、不重载。下方是常驻点餐条，13 个分类、100 多件商品横向滑轨展开，点开可加料、改规格，同一商品同规格只累加数量。

选外卖，进入单页五区工作台：填地址、选配送方式、选餐、结算、看订单进度，顶部步骤条一点即定位；配送费按「满 39 免运」实时计算，外送券会自动过滤掉标注「到店专用」的那几张。

三处细节是我最想让人看到的。一是数据都不是编的：13 家门店来自 query-nearby-stores，菜单来自 query-meals，158 项营养来自 list-nutrition-foods，15 场活动来自 campaign-calendar，优惠券与积分来自账户接口；进入页的营养计算器可以按目标热量配一餐，实时汇总热量、蛋白、脂肪、碳水与钠。二是整套视觉统一在像素语言里：Zpix 中文像素字体、2px 粗线与虚线分区、全页没有一张圆角卡片，3D 模型也做了边缘渐隐，直接落在页面底色上而不是嵌在容器里。三是它经得起点：三页共 73 项自测全绿，深链可直接定位到某家门店，所有静态资源带版本号，避免浏览器缓存旧脚本。

实现上，门店模型不是素材搬运，而是用 Blender 参数化脚本按照片比例重建、逐店导出 GLB，并在构建时校准 glTF 的灯光强度——否则网页端会整场过曝成白屏。前端不依赖框架，用原生 HTML/CSS/JS 加 model-viewer，把门店选择、购物袋、结算与昼夜主题收在少数几个状态里，三页共用一套样式和同一份数据文件，改一次数据，三页同步生效。

边界我也写清楚：外卖地址暂存在本地浏览器，结算按配置费率本地试算，真实交易链路还需要接 calculate-price 与 create-order。下一步想补的是门店座位预约与多人拼单——让「走进去」这件事真正成立。

### 方案 B · 技术拆解版（约 600 字）

**适用场景**：技术向赛道、评委多为工程师、需要体现工程能力。
**关键要素**：分层叙述（数据 / 表现 / 交互 / 校验），每条结论都给出「踩过的坑 + 解法」。

本作品是一个三页一体的像素风点餐闭环：进入页选择堂食或外卖，分别进入 3D 点餐台与外卖工作台。技术上分四层。

**数据层**：全部消费麦当劳 MCP 的真实返回——query-nearby-stores 抓取 13 家门店，query-meals 抓取 13 分类 100+ 商品，list-nutrition-foods 抓取 158 项营养并按 7 类归组，campaign-calendar 合并出 15 场活动，账户接口取优惠券与积分。抓取结果落成本地 JSON，前端只读，保证演示时不受网络与鉴权波动影响。

**表现层**：5 家门店的三维资产不是下载素材，而是用 Blender 4.5 参数化脚本按实景照片重建，一个配置文件驱动几何、材质与灯光，逐店导出 GLB。这里有一个必修的坑：glTF 的 KHR_lights_punctual 会把 Blender 的瓦特换算成 cd/lux（约 683 倍），three.js 却直接当光强用，不缩放就整场过曝；构建脚本统一乘一个系数后才可用。富士山店是黄昏场景资产，单靠曝光做不出可信白天，于是改为「一套几何、两版材质」，导出日/夜两个 GLB，前端两个 model-viewer 叠放，切换前同步机位再交叉淡化 1.4 秒。

**交互层**：全页无圆角卡片，用 2px 粗线与虚线分区；3D 区禁用缩放与平移，只锁半径允许环绕，视角预设共用同一半径，因此不会破坏「不可缩放」的约束。购物袋是唯一数据源，行结构为「商品编码 + 规格 + 数量 + 单价」，快捷加购与详情页默认搭配同源，所以两条入口加的是同一行。外卖页做成单页五区，步骤条 scrollIntoView 定位，地址表单内联展开而非弹层——移动端弹层曾出现点击失效，改为内联后彻底解决。

**工程校验**：三页各带一套自测，进入页 19 项、堂食台 28 项、外卖台 26 项，共 73 项，结果直接写进页面标题；另留 QA 参数强制昼夜、强制欢迎弹窗，便于回归与截图。

**已知边界**：外卖地址接口当前返回空列表，暂存 localStorage；结算为费率本地试算，真实下单需接 calculate-price → create-order。

### 方案 C · 精简版（约 250 字）

**适用场景**：字数受限的输入框、路演口播稿、报名表摘要。
**关键要素**：只留「是什么 + 怎么用 + 最亮的点 + 技术一句 + 边界一句」。

一个看得见的麦当劳点餐台：用 WorkBuddy 调度麦当劳 MCP 的真实数据，把点餐做成可以走进去的 3D 门店。选堂食，可在 5 家按实景建模的门店间切换，环绕看店、滑轨选餐、加料改规格；选外卖，在单页五区里填地址、选配送、结算并跟踪订单进度。门店、菜单、158 项营养、15 场活动与优惠券全部来自真实接口，进入页的营养计算器能按目标热量配一餐并实时汇总各项指标。视觉统一在像素语言里：Zpix 字体、粗线分区、无一张圆角卡片，18:00 后自动入夜，富士山店备有日、夜两套模型交叉淡化。技术上用 Blender 参数化脚本重建门店并校准 glTF 灯光，前端原生 HTML/CSS/JS + model-viewer，三页共 73 项自测全绿。当前结算为本地试算，真实交易链路与座位预约为下一步。

### 方案 D · 场景故事版（约 450 字）

**适用场景**：需要打动非技术评委、用于视频脚本或图文长帖。
**关键要素**：第二人称代入，一次完整的「从进门到吃上」的经验，功能点嵌在动作里。

假设你现在就想吃一份麦辣鸡腿堡。打开页面，先被问一句：堂食，还是外卖。

选堂食，屏幕右侧缓缓转出一间店——你可以拽着它转一圈，看清招牌、门头、落地窗，但拉不近也推不远，就像站在马路对面看它。左边写着这是广州沙面店。往下滑，13 个分类排成一条横向滑轨，点开汉堡，能加芝士、换成套餐，价格实时跳动；加进购物袋，再点一次同样的搭配，它不会多出一行，只是数字从 1 变成 2。

如果此刻是晚上八点，整间店已经自己亮了灯；富士山店甚至有两副面孔，白天是石材与玻璃，入夜是暖光和射灯，切换只花 1.4 秒，中间没有一次闪烁。

换成外卖也一样顺：地址填在页面里而不是弹窗里，配送费满 39 就自动抹掉，标注「到店专用」的券不会出现在结算区——因为它本来就不该出现。下单后进度条自己往前走：已支付、制作中、配送中、已送达。

这些店、这些菜、这些数字都不是摆设。门店、菜单、158 项营养、15 场活动，全部来自麦当劳 MCP 的真实接口；进入页还能按目标热量配一餐。它现在还不能真的把钱付出去——这是下一步——但它已经是一间你能走进去的店了。

## 四、取舍建议

- **只填一次、赌综合分**：名称 A + 一句话 A + 说明 A。
- **技术赛道**：名称 B + 一句话 D + 说明 B。
- **传播 / 人气赛道**：名称 C 或 D + 一句话 C 或 E + 说明 D（或 A 的精简）。
- **字数被卡**：直接用说明 C，250 字覆盖全部要点。
- **共同禁忌**：不要写「赋能」「一站式」「全新范式」；不要出现对不上的数字；「集合了 MCP 的功能」这类只有手段没有结果的表述，一定要补上形态与体验。
